# DevOps (Terraform on AWS)

```
terraform/bootstrap/   one-time per account: state bucket + GitHub OIDC deploy role
terraform/app/         the application stack (one state per env: app/<env>.tfstate)
terraform/app/env/     <env>.tfvars (dev, prod)
terraform/modules/     network (public + private subnets), gateway (Kong EC2, NAT), backend (private EC2), web (S3 + CloudFront, /api/* -> gateway)
gateway/kong.yml       Kong routes + plugins (rate limiting, request ids, ...); deployed live, no restart
scripts/               tf.sh, deploy-gateway.sh, deploy-backend.sh, deploy-web.sh, ssm-run.sh  (run INSIDE GitHub Actions only)
project.env            generated by the Setup workflow (no secrets, committed)
```

## Rules

- Terraform runs only in GitHub Actions. Locally you edit HCL and run
  `terraform fmt -recursive devops/terraform`; CI runs `validate`.
- Preview with `make plan ENV=dev` (plan.yml). PRs touching `devops/` get the
  plan as a PR comment automatically.
- Apply = `make deploy ENV=dev COMPONENT=infra` after the user asked for a deploy.
  Never prod unless the user explicitly says so in this conversation.
- New AWS resources go in a module under `modules/`, wired in `app/main.tf`;
  expose what scripts need via `app/outputs.tf`.
- Backend secrets: store in SSM Parameter Store (`/${project}/${env}/...`), grant
  the instance role read access, and load them at startup. Never in tfvars.
- The GitHub deploy role has AdministratorAccess (trust limited to this repo).
  Suggest tightening it when the architecture stabilizes.

## Workflows

| Workflow | Trigger | Does |
|----------|---------|------|
| `setup.yml` | human, once (`make setup`) | bootstrap stack, rename template, write project.env |
| `deploy.yml` | push to main (dev) / dispatch | tf apply + gateway + backend + web, per `component` |
| `plan.yml` | PR touching devops/ / dispatch | tf plan (+ PR comment), prints outputs |
| `destroy.yml` | human only | tf destroy with typed confirmation |
| `mobile-release.yml` | dispatch | EAS build (+ store submit) |

## Deploy flow

push to main -> `.github/workflows/deploy.yml` -> tf apply (dev) -> render +
validate `gateway/kong.yml` -> S3 -> SSM runs `/opt/gateway/deploy.sh` (applied
live via Kong's admin API; rejected configs keep the old one) -> build Go binary
-> S3 -> SSM runs `/opt/app/deploy.sh` (health check + auto rollback) -> build
web -> S3 sync -> CloudFront invalidation.

## Gateway (Kong)

- Edit `gateway/kong.yml` for routes and plugins (auth, rate limits, headers),
  then `make deploy ENV=dev COMPONENT=gateway`. CI validates it with
  `kong config parse` on every push.
- `${...}` placeholders are filled per env by `scripts/deploy-gateway.sh` from
  Terraform outputs. Add new ones there and in the CI `gateway` job.
- Keep the `X-Origin-Verify` header match on every route: it is what stops
  other CloudFront distributions from using this gateway.
- The backend is only reachable from the gateway's security group. Never give
  it a public IP or open its security group to the internet.
- Gateway logs (Kong access + errors): CloudWatch log group `/<project>-<env>/gateway`.
- The gateway instance is also the private subnet's NAT. If it is down, the
  backend loses outbound internet (S3 still works through the VPC endpoint).
